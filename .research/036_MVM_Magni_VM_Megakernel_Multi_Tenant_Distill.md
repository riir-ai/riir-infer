## TL;DR

mvm is an open-code, results-backed reproduction of the Flapping Airplanes "kittens" VM class: ONE persistent CUDA kernel takes over the whole GPU and interprets a task graph, so a whole training run, live inference on the weights being trained, and real Doom share the GPU in a single launch. For this workspace it lands three ways:

1. **Corroboration (third independent data point).** Its measured regime map — wins ONLY on small dependent work / many small runs (2.2–3.8× over PyTorch's fastest variant on small MLPs), loses GEMM-bound rows (0.34–0.73×), 162M training ~6× behind bf16 eager, decode bandwidth-bound ("decode has little headroom… ceiling 1.15–1.24×") — independently confirms the cost model this corpus already owns (gpu_07 occupancy trap, gpu_44 register-envelope, gpu_57 measured-negative ledger) and Research 30's ablation (graphs+PDL ≈ megakernel; fixed envelopes cost GEMMs 1.2–1.5×; memory preloading 3.3%). mvm's own "Where a VM wins and loses" section states the same law in the same words.
2. **The genuinely new slice vs the published class** (MPK/Mirage, Hazy megakernels, CMU lecture — all single-model inference): **intra-kernel MULTI-TENANT co-scheduling** — training windows + serve requests gated on exact weight versions + a real-time game with a checked 35 Hz cadence, all task-graph interleaved with per-class ready rings, EDF reservations, priority inheritance, and per-task version-coherence verification (184/184 version-carrying tasks exact). No published system found doing this slice (§4); Flapping Airplanes claimed the capability ("co-optimization… weirder stuff") with no code/numbers — mvm is the first public reproduction WITH result files.

## 1. What the source is (all numbers quoted at PIN 60c42deb)

- **Shape:** frontend (`frontend/mvmfe`: GPT/Llama-GQA/MoE/MLP/ViT, bf16 storage, fusion, remat, generic traced-module training) → compiler (`runtime/compile_workload.py`: ABI v2 bundle — 64-byte task descriptors, CSR edges, typed args, weight versions — plus a deterministic CPU golden) → ONE persistent kernel (`mvm_exec.cu`: block 0 = admitter, blocks 1..N = one worker per SM) → per-task timestamp trace → timeline.
- **Scheduler** (`include/mvm_sched.*` + `adaptive/`): weighted shares, reservations, EDF, priority inheritance, overload isolation, an adaptive controller, and a bandwidth arbiter. Priority buckets: 32 FIFO rings per class (Vyukov bounded MPMC cells).
- **Weight versioning** (FRAMEWORK.md): monotone per-variable version counters; `at_least N` readers wait with no edge; **`exact N` readers get an edge reader → publisher-of-N+1** (snapshot isolation — the next update cannot overwrite while the reader runs); publishers ordered by program order, unordered publishers a compile error; a wait nothing publishes is a compile-error deadlock; extra waits become `__gate` noop tasks; the lost-wakeup park/publish race is closed with a Dekker pattern (push→fence→load vs store→fence→exchange). Memory-ordering argument documented in `mvm_exec.cuh` header comment (release-CAS publish, acquire read, barrier-ordered block propagation).
- **Executor invariants** (same header): a worker holds at most ONE task; unsatisfied waiters are PARKED on the variable's lock-free list and released by the publisher — waiters occupy no block and no queue cell; every task enqueued exactly once / popped exactly once (trace `exec_count` as runtime witness); two budgets (runnable window + parked ≤ live_cap) bound in-flight at 2×live_cap so a ring never fills; slots are a bounded NON-recycled pool with explicit error codes (no UB); bundles share state ONLY through version variables (no cross-bundle edges); `timeout` is a stall DETECTOR, not a lifetime cap.
- **Results discipline:** every claim carries a `results/<date>-a100-*` dir; a "Known failures and honest negatives" table leads the README (admission FIFO head-of-line, scheduler losses to static priority, adaptive-vs-hand-set, matmul 0.34–0.73× cuBLAS, no multi-GPU run, three root-caused flake classes with alternated-run counts). The measurement culture is kin to this workspace's (box-state, interleaved reps, byte-exact controls, negative builds detected).

**Measured regime map (their A100-SXM4-40GB rows):** 9-workload merged panel geomean 1.090× vs PyTorch's fastest variant; small dependent MLPs 2.2–3.8× (32-run hetero row 3.85×); GEMM-bound 0.34–0.73×; 162M TF32 tape 0.54×; bf16 162M step 293 ms vs torch eager 47 ms (~6×) and its CUDA graph ~31 ms (~9–10×); matmul 51.0 vs cuBLAS 105.6 TFLOP/s (0.48×); dependent hop ~5 µs (mvm.cu) / 7.0 µs dispatch+hop (executor); admission 0.2 µs/task but the ready-queue pop serializes (107 pollers race one head CAS → 9 of 106 workers busy); dispatch ceiling ~0.7M tasks/s (255-register kernel, 1 block/SM) → tasks under ~100 µs are dispatch-bound; Doom 700/700 frames byte-identical to the CPU oracle, 35 Hz held beside saturating load (0/698 gaps); single-FIFO admission put every Doom frame behind 100–300 ms of a 47k-task record — per-class budgets fix it by shedding 38% of serve requests; dynamic scheduler p99 1.7–1.8× WORSE than a global static-priority queue at equal throughput (wins only under overload: train 8–11× better than a priority queue under a serve flood); adaptive controller loses to a hand-set fixed priority (value = robustness, not numbers); `MVM_MIN_BLOCKS=2` (128-register cap, 2 blocks/SM) measured +40–60% matmul but the executor suites are untested there — flagged, not adopted.

## 2. Class landscape and what is actually new (§4 prior art, fetched this session)

The persistent-kernel/task-graph-megakernel CLASS is published and tracked: **Mirage Persistent Kernel (MPK)** — "the first compiler and runtime system that automatically transforms multi-GPU model inference into [persistent kernels]", with "an on-GPU runtime system that executes the task graph entirely within a single GPU megakernel" (CMU; arXiv 2025-12 + author blog 2026-09); **Hazy Research, "How Many Llamas Can Dance in the Span of a Kernel?"** (2025-09, interpreter-template megakernel for low-latency Llama serving); a **CMU 15-779 mega-kernel lecture** (2025-09, continuous batching + prefill/decode in one kernel); the **Awesome-MegaKernel** tracker; and the mined in-corpus family (gpu_148 sgl-nvidia-mega, gpu_152 jitengine, gpu_156 sgl-muse-mega, moeshift, ThreeRT). Research 30 already owns the ablation: Together built megakernels and deleted them; CUDA graphs+PDL reach ~98% of the megakernel on their workload; memory preloading worth 3.3%; fixed envelopes cost GEMMs 1.2–1.5×. Multi-tenant GPU sharing is also published — at the PROCESS/DRIVER level (MPS/MIG/time-slicing, priority-based real-time GPU multitasking arXiv:2311.10359, co-location schedulers).

**What mvm adds that the class did not show:** the multi-WORKLOAD intra-kernel slice — heterogeneous tenants (a training run, a serving stream on version-gated weights, a real-time game with a hard cadence SLO) co-scheduled as one task graph with per-class rings/EDF/inheritance, version-coherent reads verified per task, and a compile-time deadlock checker over the version gates. That is the kittens capability claim, reproduced with result files. It is a system demonstration, not a primitive this workspace can consume — our lanes (hand kernels + CUDA graphs + the resident decode router; bevy/wgpu game render) already sit on the winning side of every regime boundary mvm's own numbers draw.

**Pinned claim, searched:** "intra-kernel multi-workload co-scheduling (training + version-gated serving + real-time game) with compile-checked version snapshot isolation" — no published system found doing this slice; MPK-class targets single-model inference. Recorded, not claimed as our novelty: it is THEIR result, and it changes nothing in this workspace's posture.
